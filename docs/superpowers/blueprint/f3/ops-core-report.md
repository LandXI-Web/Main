## 6. 정직 항목 · 통합 요청

1. ~~정문 → 관리자 착지가 어긋난다~~ — 해결됨(정문 `HOMES.admin`이 ops-core를 가리킨다). 아래는 1차 기록이다. `v3/login/auth.js homeOf()`는 관리자를 `:8702/landxi/v3/ops/`(없으면 `:8702/landxi/ops/`)로 보낸다. 그런데 `:8702`(`serve-ops.mjs`)의 정적 ALLOW에는 `/landxi/v3/`가 없어서, v3 화면은 :8702에서 열리지 않는다. ops-core는 `:4173`에서 정문과 같은 출처라 세션이 그대로 이어진다. 권장하는 수정은 한 줄이다: `homeOf`에서 관리자이면 `'../ops-core/'`를 돌려준다. 이렇게 하면 조각 인계도 필요 없다.
   이번 영상은 정문 로그인 → **실제 세션 발급**까지 정문이 처리하고, 정문이 :8702로 이동하려는 순간만 막은 뒤(Playwright `route.abort`) ops-core를 연 것이다. 세션을 주입하지는 않았다. 스크립트는 scratchpad의 `rec.cjs`다.
2. ops-core는 세션이 없으면 정문(`/landxi/v3/login/?next=…`)으로 보낸다. 정문이 없을 때만 같은 계약(`POST /auth/login`, realm lx, 관리자만 통과)으로 자기 문을 연다. `?door=1`을 붙이면 이 문을 강제로 쓴다(테스트용).
3. 영상에서 실제로 쓰기를 한 건 **1건**이다. 결재 기록 `approve · dp-nw-change · 사유 '시범 결과 확인' · lx-admin`. 단계는 canary 그대로이고, '운영 전환'은 누르지 않았다. 그래서 지금 결재 대기는 2건이다.
4. 계정 승인(가입 요청)과 카드 발행 승인은 게이트웨이에 쓰기 API가 없어서 결재함에 넣지 않았다(죽은 버튼 0). 서버에 `GET /approvals` 목록이 없으므로, 결재함은 배포본의 `approvals`와 `/ops/tenants` 사용량에서 파생해 만든다.
5. '마지막 단계 변경 뒤의 결정'은 배포본의 `updated_at`을 기준으로 잡은 근사다. 서버는 audit_log의 롤백·이식 시각을 기준으로 삼는다. pin이나 modules만 바꿔도 `updated_at`이 갱신되므로, 그 경우 이미 받은 승인이 다시 '대기'로 보일 수 있다.
6. 남원시 GPU 시간 0 h는 게이트웨이 `usage_events`의 이번 달 값을 그대로 옮긴 것이다(남원 job 45건은 lx 계정으로 돌았거나 이전 달 것이다).
7. GPU는 쓰지 않았다(읽기 폴링만). Ollama와 vLLM에는 손대지 않았다.
