# SPIKE — scrollcam (스크롤 구동 카메라 레일, MapLibre 전용)

- 일자: 2026-08-26 (재시작 후 마감)
- 브랜치: `plan1-foundation`
- 산출물: `landxi/proto/spikes/scrollcam/` (index.html · app.js · demo-map.js ·
  scrollcam.js · rail-config.js · measure.mjs)
- 실행: `node tools/serve.mjs &` → `http://localhost:4173/landxi/proto/spikes/scrollcam/index.html`
- 계측: `node landxi/proto/spikes/scrollcam/measure.mjs` (headed Chrome 필수 —
  headless 는 rAF 를 30Hz 로 조여 fps 오진을 낸다)
- 디버그 훅: `window.__rail.seek(p)` / `.play(from,to,ms)` / `.metrics()` / `.plate(id)` /
  `.auditRail(steps)` / `.easeJoinReport()`

`index.html` 은 이미 MapLibre 데모 하나만 로드한다(`<script type="module" src="app.js">`
단일 진입점, three.js/Cesium 등 다른 렌더러 없음) — 별도로 걷어낼 잔재가 없었다.

## 0. 무엇을 만들었나

`scrollcam.js` 는 host-agnostic 레일 엔진이다(의존성 없음, 선택적으로 `gsap.parseEase`).
설계 원칙 네 가지가 소스 주석에 명시돼 있고 이번 검수에서 전부 실측으로 확인했다:

1. **스무딩은 카메라 공간이 아니라 진행값(p) 공간에서 한다.** 카메라를 직접 lerp 하면
   코너에서 레일을 벗어난다 — p 를 lerp 하면 카메라는 항상 레일 위, 시간상으로만
   뒤처진다. 되감기·게이트·자동재생이 전부 이 규칙 하나에서 파생된다.
2. **정지하면 정말 정지한다.** `|Δp| < rest(1.2e-5)` 면 스냅하고 `apply` 자체를
   건너뛴다 — 매 프레임 `jumpTo` 를 계속 부르면 부동소수 잔떨림이 화면에 남기 때문.
3. **구심 매개변수화 Catmull-Rom(α=0.5)** 로 키프레임을 잇는다. 균일 CR 은 간격이
   불규칙하면 홀드 직후 카메라가 밖으로 튀었다 돌아오는 게 실제로 보였다 — 구심
   매개변수화로 교체해 해결.
4. **화면속도 재매개변수화**(`screenSpace`) — 중심 이동을 `2^-zoom` 으로 나눠, 높은
   고도에서 이동을 끝내고 낮은 고도에서 수직 강하하게 만든다(van Wijk 플라이 감각을
   스크럽으로 옮김).

### 기각된 대안 — 이징 이음(`o-join`)

구간 경계에서 두 이징의 접선을 창(window)으로 교차시키는 방식을 시도했다가
**정량적으로 기각**했다: `expo.inOut → power4.out` 경계(p=0.800)에서 오른쪽 이징의
진입 기울기(d0≈4)가 창 안으로 외삽되며 **zoom 이 14.197 → 14.138 로 0.06 레벨(축척
4%) 역주행**했다. 속도 계단 하나를 지우려다 눈에 보이는 되감김을 만든 셈 —
결론은 "창으로 덮지 말고 **이징 선택으로 경계 속도를 맞춰라**"(`easeJoinReport()`
로 각 경계의 진입/이탈 속도비를 재고, 3배 넘는 곳만 이징을 바꾼다). 현재 `KEYS`
(`rail-config.js`)는 이 린트를 통과한 상태로 커밋돼 있다.

## 1. 계측 — 무엇을 확보했나, 무엇을 못 했나

`measure.mjs` 는 20초 자동재생 영상, 스크린샷 10장(마크 6 + 결과판 4), 레일 수학
감사, 휠/키보드 지연, 정지 잔떨림, 투영 불연속, `jumpTo` 비용, 지형/게이트 on-off
fps, 모션 감소까지 재는 풀 스위트다. **이번 검수 환경(공유 머신, chrome/node
프로세스 다수 동시 실행 — GPU 경합 확인됨)에서 두 차례 실행했으나 둘 다 완주하지
못했다.** 첫 실행은 파이프(`| tail`) 버퍼링으로 출력이 전혀 안 보였고(도구 사용
실수), 재실행은 스크린샷·영상 단계(약 40초 분량)를 마친 뒤 **약 8분째에도 응답이
없어 중단**했다 — `rail.webm` 녹화 길이가 명목 24.5초 계획 대비 **실측 53.76초**로
찍힌 것이 경합의 물증이다(같은 머신에 14개 node.exe·10개 chrome.exe 가 동시에
떠 있었다). `metrics.json`(휠 지연 p50/p95, 정지 잔떨림, 지형 on/off fps 비교,
게이트 on/off 비교, 모션 감소, `auditRail`/`measureProjectionPop`/`measureJumpCost`
수치)은 **이번 세션에서 확보하지 못했다** — 경합이 없는 환경에서 재실행 필요.

대신 **완주한 절반**(20초 자동재생 + 10장 스크린샷 + 4개 결과판, 전부
`shots/spikes/scrollcam/` 갱신됨)에서 HUD 가 그 순간의 실측치를 화면에 새기므로,
스크린샷에서 다음 숫자를 직접 읽을 수 있었다(경합 상황의 숫자이므로 절대값보다
**동작이 맞는지**로 읽는다):

| 지점 | p | fps | 프레임 최악 | 게이트(누적) | apply/skip(누적) |
|---|---|---|---|---|---|
| 20s 자동재생(콘솔 로그) | 0→1 | **75** | 31.6 ms | — | — |
| `01-orbit`(globe) | 0.02 | 62 | 25.4 ms | 0 ms · 0f | 2 / 1785 |
| `03-korea`(성층운 돌파) | 0.44 | 101 | **64 ms**(적색) | 8,572 ms · 966f | 4 / 2759 |
| `04-descent`(남원 분지, terrain pitch 54.5°) | 0.62 | ∞(정지) | 64 ms | 13,095 ms · 1710f | 5 / 3519 |
| `06-landing`(정사영상 착지, z16.4) | 0.905 | ∞(정지) | 64 ms | 18,071 ms · 2301f | 367 / 4043 |
| 결과판 `남원 드론 AOI`(z18.1, 초기화 후 비행) | — | 307 | 19 ms | **4,325 ms · 1128f** | 1711 / 0 |
| 결과판 `제주 애월`(z18.4, 초기화 후 비행) | — | 450 | 18.4 ms | **4,003 ms · 1006f** | 2055 / 0 |

**읽는 법.**
- **게이트가 실제로 개입한다** — 이게 이번 검수의 핵심 확인 사항이다. 결과판으로
  비행하는 동안(리셋 직후 측정, ~6.5초 창) **프레임의 상당수가 게이트에 걸린다**
  (드론 AOI: 1128 프레임 동안 4.3초, 제주: 1006 프레임 동안 4.0초) — 고해상 정사영상
  타일이 도착할 때까지 `p` 전진을 늦추는 설계가 z18 급 착지에서 그냥 켜져 있는 게
  아니라 **일하고 있다**는 뜻.
- **64ms 프레임 최악**이 세 지점에서 반복 관측됐다(적색 표기 = HUD 자체가 경고 등급으로
  판정). 20초 자동재생 콘솔 로그의 31.6ms 와 별개로, 스크린샷 대기 중(타일 로드·지형
  전환 근방)에 실제 긴 프레임이 있었다는 뜻 — 경합 환경 숫자라 배율은 못 믿어도
  **이 지점(성층운 돌파~착지)이 프레임 예산에서 가장 비싸다**는 순위는 신뢰할 만하다
  (하는 일이 같은 순위인 게 자연스럽다 — 타일 게이트가 가장 붐비는 지점과 겹친다).
- `apply/skip` 비율은 정지 상태(06-landing 이후, skip 4043 ≫ apply 367)에서 원칙
  2(정지 스냅)가 실제로 작동함을 보여준다 — 정지해 있는 동안 대부분의 프레임이
  `jumpTo` 호출 자체를 건너뛴다.

## 3. `dive.js` 이관 노트

현재 프로덕션 `landxi/proto/js/dive.js` + `camera.js` 는 scrollcam 과 **같은 문제를
독자적으로 풀고 있다** — 다른 이름, 다른 구현.

| 항목 | `camera.js`(현행) | `scrollcam.js`(스파이크) |
|---|---|---|
| 보간 | 키프레임 사이 **선형** + 구간별 GSAP 이징(`cameraAt()`) | 구심 Catmull-Rom(α=0.5), `tension` 로 선형까지 낮출 수 있어 **현행과 호환** |
| 이음매 전략 | 세그먼트 로컬 이징만(이음 창 없음) | **의도적으로 같은 결론**에 도달 — `join` 을 실측으로 기각(§0). 즉 현행 방식이 이미 스파이크가 검증한 "옳은 기본값" |
| 화면속도 재매개변수화 | 없음 — 위경도 직접 lerp | `screenSpace: true` — 저고도 이동이 더 "강하"처럼 읽힘 |
| 타일 게이트 | `gate()` — 강하 구간(`0.545<p<0.815`)에서 3단 스텝(`descentStep`)으로 `PA` 를 절대치만큼 전진, `isSourceLoaded()` 확인 + 12초 초과시 강제 해제 | `metrics().gate` 로 게이트 개입 시간·프레임을 **계측 가능한 형태로 노출**(§1 표), on/off 비교(`o-gate`)까지 UI 에 있음 |
| 챕터 자석 | 없음(챕터는 룰러 표시용) | `magnet` — idle 후 가까운 챕터로 스크롤 자체를 끌어당김(옵션, 기본 on) |
| 정지 스냅 | 유사 로직 있음(스로틀 기반) | `rest` 임계값으로 명시적 스냅 + `apply` 스킵 계측 |
| 잔떨림 계측 | 없음 | `met.jitZ/jitB/jitC` — 정지 중 카메라 값이 흔들리는지 직접 측정 |

**권고**: `camera.js` 를 통째로 교체할 필요는 없다 — 이음매 전략(가장 논쟁적인
부분)은 이미 같은 결론(선형 세그먼트+개별 이징, 창 금지)이다. 이관해서 얻을 실익은
① **화면속도 재매개변수화**(`screenSpace`) — 현재 남원 착지 구간(`z16.0→18.2`,
p=0.762→0.805)이 위경도 직접 lerp라 실감이 스파이크보다 덜 "강하"할 수 있다,
② **게이트 계측 노출** — 지금 `dive.js` 의 게이트는 동작만 하고 수치가 HUD에
없다, scrollcam 방식을 이식하면 실측 회귀 테스트(계측 스위트)가 가능해진다,
③ **잔떨림 계측** — 착지 후 정지 상태에서 카메라가 실제로 죽어 있는지 자동
검증할 수단이 지금 없다. 세 가지 다 **`camera.js` 를 갈아엎지 않고 계측/보조
유틸만 이식**하는 선에서 가능하다.

## 4. 판정

MapLibre 전용 레일 엔진으로서 설계는 탄탄하고(이음 창 기각처럼 실측으로 걸러낸
결정이 이미 프로덕션 `camera.js` 와 같은 결론에 도달해 있다), 게이트가 실제로
일하는 것도 이번 검수에서 확인했다. **다만 이번 세션에서는 계측 스위트를 완주하지
못했다** — 공유 머신의 GPU/CPU 경합 때문으로 보이며(53.76초 vs 명목 24.5초 영상
녹화가 물증), 코드나 레일 설계의 결함이라는 증거는 없다(부분 실행분에서 오류·NaN·
프리즈 없음). **재실행 필요**: 경합 없는 환경에서 `node landxi/proto/spikes/scrollcam/measure.mjs`
전체 스위트(휠 지연 p50/p95, 지형 on/off fps, 게이트 on/off 비교, 모션 감소,
`auditRail`/`measureProjectionPop`/`measureJumpCost`)를 다시 돌려 `metrics.json` 을
받아야 이 스파이크를 완전히 닫을 수 있다.
