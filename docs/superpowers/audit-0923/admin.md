## 0. 한 줄 판정

**서비스 관리 5쪽(사용자·공지·문의·FAQ·지도 속성)은 원본 기능 1:1로 실제 동작한다. 콘솔 오류 0, 깨진 링크 0, 법전 위반 0이다. 하지만 "완전히 다른 사이트 · 관리 기능만"이라는 요구는 첫 화면(운영 현황) 한 장에만 걸려 있다.** 운영 현황의 결재 숫자는 코드에 적어 둔 상수라서 처리해도 바뀌지 않는다. 관리자가 올린 공지와 FAQ는 사용자 화면에 한 줄도 닿지 않는다. 몰입감은 업무 목록 화면 수준이라 사용자의 품질 기준에 한참 못 미친다.

## 4. 발견 사항

### P1

**A1. 운영 현황의 결재 대기 숫자는 상수다(데이터 정직성).**
`admin-home.js:46-50` 에 `n: 2 / 1 / 6` 이 박혀 있다. 가입을 승인하고 문의에 답해도 운영 현황은 1과 6에 머문다(`52-home-after-approve.png`, `flows.json › homeAfterApprove/homeAfterReply`). 같은 저장소를 읽는 `pendingCounts()`(`admin.js:70-73`)가 이미 있는데도 쓰지 않는다. 쓰이지 않는 `approvals = window.DASH_APPROVALS` 도 남아 있다(`admin-home.js:31`). 관리자가 이 화면을 여는 이유가 결재인데, 그 숫자가 거짓말을 한다.

**A2. "완전히 다른 사이트"가 첫 화면 한 장뿐이다.**
검은 마스트헤드는 `admin-home.js:41` 이 운영 현황에서만 켠다. 서비스 관리 5쪽, 카드 발행 관리, 데이터 관리, 생산 관리, MY는 흰 마스트헤드, 직원 사이트와 같은 공지 띠, 같은 푸터(Family Site)를 그대로 쓴다(`result.json › pages.*.mastBg = rgb(255,255,255)`, `10-admin-users-1440.png`, `63-admin-produce.png`, `31-admin-on-dataset.png`). 레일 여섯 줄과 관문 말고는 직원 사이트와 구별되지 않는다. 입구도 같다. 같은 `login.html` 에서 라디오 하나로 고른다(`00-login.png`). 관리자 전용 주소나 전용 로그인은 없다.

**A3. 관리자가 올린 공지와 FAQ는 사용자에게 닿지 않는다(두 벌의 데이터).**
관리자 공지(12건, 최신 "[긴급] 정기 서버 점검 안내")는 `admin-data.js` 에 있고, 사용자 공지(8건, "고위험 탐지 건 긴급 처리 안내")는 `support-data.js` 에 따로 있다. `admin-data` 나 `lx-admin-v1` 을 읽는 사용자 화면은 없다(grep 결과 0). 그래서 관리자 사이트 마스트헤드의 공지 띠에는 **관리자가 관리하는 적 없는** 공지가 뜨고, 누르면 관리자 레일에서 뺀 `서비스 지원` 화면으로 넘어간다(`shell.js:76`, `65-admin-mast-notice-target.png`). FAQ도 같은 구조다. 반면 문의는 `admin.js:17-37` 로 이어져 있다. 공지와 FAQ를 관리하는 화면이 실제로는 아무것도 바꾸지 못한다.

**A4. 사용자 관리가 플랫폼의 3단 위계를 관리하지 못한다(9/20 역할 스펙 미충족).**
권한 선택지는 `남원시청 관리자 · 사료작물 분석 · 농지 활용 분석 · 영농 정보 분석 · 일반사용자` 다섯 개로, 남원시 한 기관의 역할이다(`admin-data.js:6`, `10-admin-users-1440.png`). `roles.js` 가 세운 LX 관리자 · LX 직원 · 영업용 계정 3단과, 그 3단에 붙은 역량(`CAPS`)을 보거나 바꾸는 자리가 관리자 사이트 어디에도 없다. 기관(테넌트)별 사용자를 나눠 보는 필터도 없다.

**A5. 모바일 390px 폭에서 여섯 쪽이 모두 깨진다.**
가로로 137~537px 넘친다. 서비스 관리 쪽은 마스트헤드의 공지와 기준일 글자가 겹쳐 읽을 수 없다(`20-admin-users-390.png`). 운영 현황은 관리 네 축의 이름이 잘린다("분석서비스", "개")(`20-admin-home-390.png`).

### P2

**A6. 레일 활성 표시가 틀렸다.** 운영 현황에서도 `서비스 관리` 에 불이 켜진다. `admin-home.js:34` 가 `active: 'admin'` 을 넘기기 때문이다(`rail.mjs` 출력 `cur:["서비스 관리"]`). 게다가 운영 현황과 서비스 관리의 아이콘이 둘 다 `gear` 이다(`shell.js:31,43`). 레일 여섯 줄이 위 2개와 아래 4개로 갈라져 가운데가 약 400px 비어 있다(`10-admin-home-1440.png`).

**A7. 기준일이 한 사이트 안에서 셋이다.** 운영 현황과 카드 발행은 `2026.06.08`, 서비스 관리는 `2026.04.23`, 마스트 공지가 여는 서비스 지원은 `2026.04.22` 이다. 지도 속성 수정 일시만 실제 벽시계(`2026.09.23`)를 쓴다(`admin-map.js:87` 의 `stamp()`). 콘티 시각 규칙(`admin.js:39-60`)을 스스로 어긴다.

**A8. 같은 GPU 수치가 두 값으로 나온다.** 운영 현황 한눈 수치는 `GPU 2,337 h/년`(추론만, `infra.js:94`)이고, 같은 사이트 생산 관리 › 인프라는 `2,517 h/년`(추론 + 재학습, `produce.js:374`)이다. 차이를 설명하는 문구가 없다(`10-admin-home-1440.png` vs `63-admin-produce.png`).

**A9. 결재 카드의 딥링크가 약하다.** `카드 발행 승인 2` 를 누르면 `admin-publish.html` 전체 목록이 열린다. 원본 KPI는 `?status=대기` 로 곧장 걸러 주었다(인벤토리 §8, 177·251행). 가입 승인과 미답변 문의는 첫 대기 건(`?id=18`, `?id=115`)을 선택한 채 열리므로 문제없다.

**A10. 거절(denied)을 알리지 않는다.** 권한 없는 화면에서 `?denied=` 를 달고 돌아오지만 운영 현황은 이 값을 읽지 않는다(`flows.json › deniedMsg=false`). 왜 튕겼는지 모른다.

**A11. 운영 현황 1920 폭이 비어 보인다.** 네 축 카드가 590px 높이에 숫자 세 줄씩만 둔다. `space-evenly` 로 벌려 놓아 칸마다 빈 띠가 100px 넘게 생긴다(`20-admin-home-1920.png`, `admin-home.css` `.ah-ax-r`). 법전 §6의 "빈 띠 80px 초과 금지, 키우지 말고 콘텐츠로 채운다"에 걸린다.

### P3

**A12. 조치 숫자의 색이 다르다.** 법전 §2는 `가입 승인 대기 · 미답변 문의` 큰 숫자를 경고색으로 쓰라고 한다. 사용자 관리 밴드는 빨강 `1 건 승인 필요` 인데 운영 현황 결재 대기는 파랑 `1` 이다(`10-admin-home-1440.png` vs `10-admin-users-1440.png`).

**A13. 역할 선언이 섞여 있다.** 관리자의 `caps` 에 `build · run · edit · request` 가 남아 있다(`roles.js`). 메뉴에서 해당 화면을 뺐으니 지금은 해가 없지만, "관리 기능만"이라는 선언과 어긋난다.

**A14. 개발 구현 · 인프라 관리는 생산 관리의 탭으로 넘기는 링크일 뿐이다.** 관리자 사이트 안에 인프라 증설 결재, 배포본 승인, 기관 요구 처리 같은 **결재 동작**이 없다. 모두 "보는" 화면이다.

## 6. 사용자 품질 기준 대비 — 3 / 10

- **좋은 점:** 모든 컨트롤이 실제로 동작한다. URL이 상태를 들고 있어 새로고침과 공유에 강하다. 지도 속성 관리의 **실지도 미리보기**(값을 바꾸면 즉시 다시 그림)만이 이 영역에서 "동작하는 화면으로 판단"하는 사용자에게 먹히는 순간이다(`59-map-edit-night.png`).
- **모자란 점:** 운영 현황은 흰 바탕에 숫자 격자뿐이다. 움직이는 것, 지도, 시계열, 공간 맥락이 하나도 없다. 관리자가 보는 것이 "전국 어디에 무엇이 배포돼 돌고 있나"인데 그것을 지도나 필름으로 보여 주지 않는다. 서비스 관리 5쪽은 원본 게시판을 정돈한 수준이다. 사용자가 여러 차례 거부한 '딱딱한 업무 시스템 목업'의 문법에서 벗어나지 못했다. 법전 §4의 유휴 요소(실데이터에 묶인 움직임 1개)도 운영 현황에 없다.

## 7. 권고 (우선순위)

1. **A1:** 결재 대기를 `pendingCounts()` 와 발행 대기 저장소에서 계산한다. 탭 숫자와 같은 값을 쓰게 한다.
2. **A3:** 공지와 FAQ를 한 저장소로 합친다. 사용자 공지 화면과 마스트 공지 띠가 관리자 저장소를 읽게 한다. 관리자 사이트의 공지 띠는 없애거나 "게시 중 공지 n건 · 팝업 1건" 같은 관리용 띠로 바꾼다.
3. **A2:** `data-site=admin` 을 관리자 역할 전체(서비스 관리, 발행, 데이터, 생산, MY)에 적용한다. 관리자 전용 입구(`admin/login` 또는 역할 고정 URL)와 푸터를 따로 둔다.
4. **A4:** 사용자 관리에 `구분: LX 관리자 / LX 직원 / 영업 / 기관(남원·…)` 패싯과 역할 변경 기능을 넣는다.
5. **A6 · A7 · A8 · A10:** 레일 키를 `ops` 로, 아이콘을 분리한다. 기준일은 하나로 통일한다. GPU 수치에 구분 문구를 단다. `?denied` 를 안내한다.
6. **몰입감:** 운영 현황의 가운데를 실제 배포본 7개와 적용 기관 3곳을 찍은 **전국 배포 지도**(MapLibre, 배포본별 상태, 대기 결재 위치)로 채운다. 결재 카드는 요청 지역 실크롭(EVIDENCE-PAIR)을 붙인다. 이것이 "관리자는 본다"는 선언에 맞는 화면이다.
7. **A5:** 390 폭에서 분할 판을 목록 → 열람의 두 단계로 접는다.
