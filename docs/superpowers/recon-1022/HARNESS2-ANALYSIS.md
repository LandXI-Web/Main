있다. https://github.com/google-research/harness2 (404 아님).
- 만든 날 2026-10-06, 마지막 반영 2026-10-13(저장소 기록상 커밋 메시지 "Fix arXiv link"), 별 약 1만 7천 개, 포크 약 1천 7백 개, 열린 이슈·요청 119건(이슈와 풀리퀘스트가 합쳐진 수).

- 저장소 용량 약 15MB, 핵심 코드 약 6,700줄(harness2/core, harness2/substrate).

## 2. 한 문단 요약
"하네스"는 모델 둘레의 모든 것(시스템 프롬프트, 규칙, 기억, 도구 설명, 하위 에이전트, 기술(skills), 보조 스크립트, 플러그인)을 말한다. Harness²는 모델 가중치는 그대로 두고 이 둘레를 **작업마다 자동으로 고쳐 나가는 틀**이다. 작업 하나를 돌려 보고, 고칠 점을 제안하고(Propose), 후보 하네스로 같은 작업을 다시 돌려 비교하고(Probe), 실행 차이를 근거로 합친(Compose) 하네스를 만든다. 정답 채점 없이 실행 기록의 차이만으로 고친다. 그 결과와 배운 점은 "개선용 하네스"에 쌓여 다음 작업에 쓰인다. 즉 **채팅 에이전트 자체가 아니라, 에이전트의 프롬프트·규칙·도구 설명을 자동으로 다듬는 연구용 실험 도구**다.

## 3. 구성과 동작 (파일 경로)
저장소 루트: `harness2/`
- `core/recursion.py` — 병렬 모드(후보 k개 동시 탐색)와 순차 모드(k번 이어서 다듬기). 모드당 실행 4k번, 개선 단계 3k번. 잘못된 제안은 한 번 다시 시도하고, 그래도 안 되면 현재 하네스를 그대로 쓴다.
- `core/proposer.py`, `core/prompts.py`(1,163줄) — 개선 담당 모델 세션. 작업 폴더를 격리해 파일을 읽게 하고 제안을 받는다.
- `core/selection.py` — 완성된 결과물들을 이름 가리고 하나 고른 뒤, 근거 있는 교훈을 남긴다.
- `core/tree.py`, `core/library.py`, `core/ledger.py` — 하네스 파일 묶음 관리, 지난 작업에서 얻은 하네스·교훈 보관, 비용 기록.
- `core/judge.py` — 선택이 끝난 뒤에만 채점. 방법 본체는 이 모듈을 가져다 쓰지 않는다(채점 정보가 개선에 새지 않게 분리). 채점 실패는 0점이 아니라 "없음"으로 빼서 센다.
- `substrate/opencode.py`, `substrate/codex.py` — 실제로 일하는 에이전트(OpenCode 또는 Codex) 연결부.
- `benchmarks/` — JobBench(직무 업무), LAB(법률 업무), WorkBuddy-Bench(사무·웹·코드) 어댑터. 세 가지 모두 사무·법률·직무형 과제이고 **지도·영상·GIS 과제는 없다.**
- 명령: `harness2`(실행), `harness2-judge`(채점), `harness2-report`(보고), `harness2-setup`, `harness2-check`, `harness2-demo`(모델 키 없이 돌아가는 시험 실행), `harness2-bridge`(Vertex를 Responses API로 노출).
- 하네스 예시 파일: `third_party/jb_runner/harness_baseline_oc/` (`harness.yaml`, `systemprompt.md`, `guardrails.md`, `LongTermMEMORY.md`, `tool_descriptions/tool_guidance.md` …). 고칠 수 있는 부분을 파일로 나눠 둔 방식이 핵심이다.

## 4. 라이선스와 사용 제한
- 본체는 Apache 2.0 — 가져다 쓰기·고쳐 쓰기 자유(고지 유지).
- `third_party/` 아래는 각자 원래 라이선스: JobBench Apache 2.0, LAB MIT, OpenCode MIT, **WorkBuddy-Bench는 Tencent 자체 라이선스이고 유럽연합 안 사용에 지역 제한이 있다**(dependencies/README.md). Land-XI가 이것을 가져올 일은 없다.
- 보안 주의: README가 "실행 에이전트의 네트워크는 제한이 없고, Codex는 샌드박스를 끈 채 돈다"고 적었다. 신뢰하지 않는 환경에서 그대로 돌리면 안 된다.

## 5. 성숙도
- 별이 매우 많지만 만든 지 약 2주, 버전 0.1.0. 연구 논문 공개용 코드이고 운영 서비스용이 아니다. 열린 이슈·요청 119건.
- 시험은 `tests/test_workflow.py` 하나뿐. 논문이 주장하는 효과는 사무·법률·직무 과제에서 Gemini 3.5 Flash, GLM-5로 낸 것이다(README 기준 최대 11.5점 등). 우리 분야(도구 호출형 지도 에이전트)에서의 효과는 확인된 바 없다.

## 6. 필요 조건
- Linux + Python 3.12(3.13도 가능), uv, Node.js 20 이상, Google Cloud CLI. LAB은 Pandoc·Poppler, WorkBuddy는 Docker. **Windows는 공식 지원 아님**(pyproject 분류가 POSIX).
- 모델: 기본 설정은 Google Vertex AI의 Gemini(실행·채점), 개선 담당은 Vertex의 Claude 또는 Gemini. Vertex 프로젝트·인증이 필요하고 호출마다 API 비용이 든다. 실행은 OpenCode의 "공급자/모델" 형식이라 이론상 다른 공급자도 붙일 수 있으나, 공급된 설정과 검증은 Vertex 기준이다. 우리 vLLM 로컬 모델을 붙일 수 있는지는 이번에 시험하지 않았다(OpenCode가 OpenAI 호환 주소를 받는지에 달렸다).
- GPU는 필요 없다(모델은 원격 API). 개선 한 번에 모델 호출이 많이 든다(설계상 실행 4k번 + 개선 3k번).

## 7. Land-XI 와의 관련성 (솔직한 판단: 낮음~보통, 통째 도입은 비추천)
Land-XI의 XI ChatGEO는 vLLM 위에서 도구를 불러 지도를 제어하는 에이전트이고, 우리 작업은 GPU 작업 대기열과 항공영상 변화탐지다. Harness²는 사무·법률 과제용 연구 틀이라 그대로 맞지 않는다. 다만 **발상 세 가지는 쓸 만하다.**

도움이 될 수 있는 곳
1. **ChatGEO 지침 파일 나누기.** 시스템 프롬프트, 규칙, 도구 설명, 기억을 파일로 분리해 한 곳씩 고치고 되돌리는 방식(`harness.yaml` 형태). 지금 ChatGEO 지침이 한 덩어리라면 나누는 것이 시험·되돌리기에 유리하다. 이건 코드 도입이 아니라 구조만 참고.
2. **400문항 시험을 개선 루프의 눈금으로.** Harness²의 "채점 정보는 개선 쪽에 보여 주지 않고, 선택 뒤에만 채점"하는 분리 원칙(`core/judge.py`)은 우리 400문항에도 적용된다. 개선용 문항과 최종 확인용 문항을 갈라 두면, 시험 문제에 맞춰 지침을 외우게 만드는 실수를 막는다.
3. **같은 질문을 후보 지침 여러 개로 돌려 실행 기록을 비교.** 도구를 잘못 부르거나 헛도는 지점을 실행 차이에서 찾는 방식. 우리는 사람이 400문항 결과를 보고 고치고 있으니, 이 비교를 반자동으로 만드는 아이디어로 참고할 수 있다.
4. 실패 처리 원칙: 채점 실패를 0점이 아닌 "없음"으로 빼는 것, 잘못된 제안은 한 번 재시도 후 기존 상태 유지하는 것은 우리 작업 대기열·시험 도구에도 그대로 옮길 수 있는 습관이다.

쓰지 말아야 할 것
- 저장소 전체 도입·설치: Linux 전제, Vertex 의존, 샌드박스 꺼진 에이전트 실행, 호출량 큼. 우리 GPU 200W 규칙과도 무관하게 외부 API 비용만 늘린다.
- 자동으로 지침을 계속 고쳐 운영 ChatGEO에 바로 반영하는 구조: 우리는 "확인받고 만든다" 규칙이 있다. 자동 개선 결과는 반드시 사람이 확인한 뒤에만 반영해야 한다.
- 벤치마크(JobBench·LAB·WorkBuddy): 사무·법률용이라 지도·변화탐지와 무관. WorkBuddy는 지역 제한 라이선스.
- 대기열·장시간 작업 처리: 이 저장소는 장시간 작업 게이트웨이가 아니고 단순한 스레드 풀(`ThreadPoolExecutor`)과 재시도 수준이라 우리 GPU 대기열에 참고할 것이 거의 없다.
- 항공영상 변화탐지: 관련 내용 없음.

## 8. 이런 것도 필요하지 않을까요? (제안, 채택은 사용자 결정)
1. **ChatGEO 지침을 파일로 나눠 보관**: 말투·금지 규칙·도구 설명·기억을 따로 두면 400문항 시험 결과가 나빠졌을 때 어느 부분이 원인인지 바로 되돌릴 수 있다. 누가 필요한가 — 지침을 고치는 개발자와 결과를 확인하는 사용자.
2. **400문항을 "고치기용 / 최종 확인용"으로 나누기**: 고친 지침이 시험 문제만 맞추는지 가려낼 수 있다. 누가 필요한가 — 품질을 보증해야 하는 사용자와 외부 설명이 필요한 영업.
3. **도구 호출 실패 사례를 모아 비교하는 작은 보고서**: 같은 질문에서 지침 두 안이 어디서 갈렸는지 한 장으로 보여 주면 검수가 빨라진다(Haiku 여러 개로 모으고 Sonnet이 판정하는 기존 재검수 방식에 얹을 수 있음).
