# 설계 7차 · 영상 표준 하나로 · 용량 줄이기 · ECW 받기 — 한 장 요약

> 2026-10-01 · 오퍼스 5.5. 지위: **사용자 확인 전 조사 · 시험 · 설계** — 서버 코드 수정 0 · GPU 0. 사용자 10-01 지시 "ECW 형식도 바로 받을 수 있는지? 관리 관점에서 한번 더 검토하고 해야겠다. ecw, tif, COG 등 복잡한 형식을 표준화하되, 최대한 용량 다이어트도 필요하겠는데."(원칙 94)를 받아, 이 PC 에서 형식마다 실제로 열어 보고, 실제 영상 네 표본을 CPU 만으로 압축 방식별로 바꿔 쟀다. 시험 파일은 끝나고 지웠다.
> 어느 플랫폼: **둘 다**(LX 직원의 데이터 올리기 · 기관의 분석 의뢰가 같은 길로 받는다). 그림은 저장소에 올리지 않는 `shots/` 에 있어 확인 요청 페이지에서 보인다(`python docs/superpowers/final/process/design-r7/imagery-std/shoot.py --chips`).

## 한 장 요약
| 물음 | 답 | 자세히 |
|---|---|---|
| **ECW 를 바로 받을 수 있나** | **지금은 못 받는다.** ECW 를 읽는 구성요소는 Hexagon(옛 ERDAS) 것뿐이고, **PC 에서 읽기는 무료 · 서버에서 읽기는 유료**(값 비공개 · 서버 CPU 코어 수 기준 견적). 무료 길 = 보내는 쪽 PC 에서 QGIS 로 'JPEG 압축 GeoTIFF' 로 바꿔 올리기(이 PC 의 QGIS 로 실제 ECW 를 바꿔 봄 — 됨) | `formats.md` 2절 · `shots/std-5-ecw.png` |
| 다른 형식은 | GeoTIFF(무압축 · LZW · JPEG) · COG · IMG · JPG + 좌표 파일 · JP2 — **모두 읽힌다**. 단 JP2 는 영상을 '바꾸는' 쪽 도구가 못 읽는다(무료 구성요소 하나로 해결) | `formats.md` 1절 |
| 지금 고칠 것 | 분석 의뢰 화면이 ECW 를 받는다고 안내하고, **20GB 까지 다 올린 뒤에야** "읽을 수 없습니다"가 뜬다 → 파일을 고르는 순간 안내 | `formats.md` 1절 |
| 표준 하나 | **COG · JPEG 90 · 개요 포함 · 빈 칸은 마스크** · 좌표계는 번호만 정리(다시 그리지 않음) · 16비트 위성 · 다중분광 · 높이 값은 무손실 | `policy.md` 2절 |
| 얼마나 줄어드나(실측) | 25cm 항공 도엽 **원래의 9.0~13.3%**, 드론 정사(LZW) **10.6~18.0%**(개요까지 넣은 크기) | `diet.md` 2절 · `shots/std-2-diet.png` |
| 화질 | 가장 나쁜 표본도 PSNR **39.8dB** · 구조 유사도 **0.980** — 눈으로 원본과 구별이 어렵다. JPEG 80 · WEBP 80 은 복잡한 항공에서 잔결이 뭉개짐 | `diet.md` · `shots/std-3-chips.png`(공개 영상 조각) |
| 빨라지는 것 | 드론 원본(줄 단위 · 개요 없음)은 축소 화면 한 장에 **5.7초** — 표준본은 수천분의 1초 | `diet.md` 3절 |
| 지금 보관 영상에 적용하면 | **5,907GB → 568~881GB(85~90% 줄어듦 · 추정)**. 단 이미 쌓인 LX 원본을 지울지는 사용자가 정함 | `policy.md` 4절 · `shots/std-4-manage.png` |
| 시간 · 대기열 | 도엽 한 장 5~8초(CPU 4개) · 새 영상은 바로 · 쌓인 5.9TB 는 밤 이틀 안팎(추정) · **GPU 0** | `policy.md` 5절 |
| 원본 | 표준본 확인 뒤 **30일** → 정리 목록 → **LX 관리자**가 한 번 눌러 지움(기록). 규칙은 관리자 설정 한 곳 | `policy.md` 3 · 6절 |
| 분석용 · 보기용 | **나누지 않는다** — 표준본 한 벌이 지도 · AI 분석 · 기관 지도를 다 맡는다 | `diet.md` 5절 |
