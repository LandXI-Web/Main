# 못 한 요청 → 서비스 개선 고리

> 2026-10-01 사용자: "서비스를 개선하는 측면에서? 뭔가 사용자가 못 하는 걸 확인했다. 이걸 개선할 수 있도록 하는 방향도 설계에 들어가야 한다."
> 지위: 사용자 확인 전 제안(코드 수정 0). 원칙 57(먼저 제안) · 34(확인받고 만든다) · 39(계정 범위 밖 0) · 59(개인정보는 정책과 함께) 안에서 그린다.

## 한 줄
XI ChatGEO 가 **못 한 요청**을 저절로 모아 → 비슷한 것끼리 묶어 '자주 막히는 일' 목록으로 → LX 가 **채택 · 보류 · 이미 됨**을 고르고 → 만들어지면 그걸 물었던 사람에게 **"이제 됩니다"** 가 간다. 확인 대장(사용자 확인 → 구현) 흐름의 **입구**가 하나 더 생기는 것이고, 판단 권한은 그대로 사용자·LX 관리자에게 있다.

## ① 무엇을 저절로 모으나(채팅창 · 서버)
| 신호 | 어떻게 잡나 | 남기는 것 |
|---|---|---|
| 못 한 요청 | 답이 규칙 ② 틀(이유 + 대신 + 버튼)로 끝날 때 — 서버 검증기가 동작 문장을 지웠거나, 도구가 '없는 기능 · 이 화면에 없음 · 자료 없음 · 권한' 상태를 냈을 때 | 분류(아래 표) · 요지 한 줄(예: '두 시점 영상 비교') · 역할 · 화면 · 지역 단위(시군구까지) · 때 |
| 막힌 동작 | 화면 끝 신호가 '못 함'(지도 없음 · 층 없음 · 처리 못 함) | 동작 이름 · 화면 |
| 같은 뜻 재질문 | 같은 대화에서 **3분 안에** 앞 질문과 뜻이 같은 질문(지명·동작·조사만 다름)을 다시 보냄 | '다시 물음' 표시 1 |
| 도움 안 됨 | 답 아래 작은 두 버튼 **'도움 됐어요 / 도움 안 됐어요'**(원칙 50 — 메모 강요 0, 누르면 끝) | 표시 1 · 누른 사람은 그 요청에 묶임(알림용) |
| 취소 | 확인 카드에서 취소를 누름 | 취소 1(실행 카드가 잘못 뜬 것일 수 있음) |

**보관 범위(개인정보 · 원문).** 대화 **원문은 저장하지 않는다**. 남기는 글은 서버가 만든 **요지 한 줄**(지명·지번·사람 이름은 '○○'으로 가림 — 이미 있는 가리기 그대로)과 분류 코드. 누가 물었는지는 **알림을 보내기 위해서만** 계정 번호로 묶고 90일 뒤 지운다(원칙 94 의 90일과 같은 기간). 기관 계정의 요청은 그 기관 담당 프로젝트장과 LX 관리자만 본다(원칙 39 · 72). 사용 현황의 '요청 건수'(원칙 91)와 같은 표에서 계산한다 — 숫자 한 출처.

분류(여덟 가지 · 새 분류는 LX 관리자가 더함): **지도 동작 없음** · **이 화면에 없음** · **자료 없음(지역)** · **권한 밖(관할·역할)** · **법령 못 찾음** · **필지 못 찾음** · **서버 응답 없음** · **그 밖(모델이 못 알아들음)**.

## ② '자주 막히는 일' 목록 — 비슷한 것끼리 묶기
- 묶는 열쇠 = 분류 + 요지의 핵심 낱말(동작 · 대상). 예: '두 시점 영상 비교' · '지적선 켜기' · '우리 시 몇 건' 은 각각 한 줄이 된다.
- 한 줄에 보이는 것: **요지 · 몇 번(이번 달 / 전체) · 어느 역할(LX 직원 · 관리자 · 기관) · 어느 화면 · 다시 물음 몇 번 · 도움 안 됨 몇 번 · 마지막 때**. 지역은 시군구 수만("3개 시군구").
- 정렬 기본값 = 많이 막힌 순. 필터 = 역할 · 화면 · 분류 · 상태.
- 숫자는 모두 서버 표에서(지어낸 운영 서사 0 · 큰 숫자 자리엔 '이번 달 막힌 요청 n건'처럼 업무 결과만).

## ③ LX 쪽 화면 — '개선 후보' (누가 보나 · 무엇을 누르나)
| | |
|---|---|
| 어디 | **LX 관리자 대시보드 → 배포(서비스 관리) 메뉴 → 개선 후보** 탭 하나(배포 · 되돌리기 옆). 담당 프로젝트장은 **LX 직원 대시보드 → 요청함**(원칙 81 의 요청함)에 **자기 서비스·관할 기관에서 온 것만** 같은 모양으로 본다. 새 메뉴를 만들지 않는다. 시안 `mock/candidates.html` · `shots/new-e-candidates.png`. |
| 누가 | LX 관리자(전부) + 그 서비스·기관의 담당 프로젝트장(자기 것) — 원칙 72 '관리자는 다 보고 돕는다'. |
| 한 줄 | 요지 · 몇 번 · 역할 · 화면 · 분류 · 상태 · 마지막 때 · 예시 질문 2개(요지만 · 원문 아님). |
| 누를 것 | **채택**(개발할 일로 — 확인 대장에 '확인 대기' 항목이 만들어짐, 아래 ⑤) · **보류**(사유 한 줄 · 다시 보기 날짜) · **이미 됨**(안내 문구 한 줄 적음 → 다음부터 같은 요청에 그 문구와 버튼이 바로 나감 · 개발 없음). 반려는 없다(막힌 요청은 틀린 요청이 아니다). |
| 상태 | 새로 옴 → 채택(개발 중) → 만들어짐(알림 보냄) / 보류 / 이미 됨. |
| 일상어 | 화면 글은 "자주 막히는 요청" · "채택 · 보류 · 이미 됨" · "이제 됩니다 알림" — 분류 코드 · 도구 이름 0. |

## ④ "이제 됩니다" 알림
- 채택한 것이 **배포되어 사용자 확인(구현 확인)까지 끝나면** 관리자가 그 줄에서 '이제 됩니다 보내기'를 누른다(자동 발송 아님 — 사람이 보내는 한 줄).
- 받는 사람: 그 요청을 했던 계정(90일 안) — 다음에 채팅창을 열 때 **맨 위 한 줄** "지난번에 물으신 '두 시점 영상 비교'가 이제 됩니다 · `해 보기`"(누르면 그 질문이 보내짐 · ×로 닫으면 다시 안 보임). 메일·문자는 쓰지 않는다(원칙 89 — 알림 수단은 정식 오픈 때). 시안 `mock/talk.html?s=f` · `shots/new-f-nowworks.png`(휴대폰 `-m`).
- 기관 사용자에게도 같은 한 줄(기관 분기 화면의 채팅창). LX 관리자 · 담당 프로젝트장은 보낸 기록을 본다.

## ⑤ 확인 대장(사용자 확인 → 구현)과 잇는 법
```
못 한 요청 ─ 저절로 모임 ─ 자주 막히는 일 목록 ─ LX 관리자 '채택' ─▶ 확인 대장 '확인 대기' 한 줄(무엇 · 몇 번 · 역할 · 제안 방법)
                                                                      │
                                                   사용자 확인 ─ 구현 ─ 구현 확인 ─▶ 관리자 '이제 됩니다 보내기' ─▶ 물었던 사람에게 한 줄
```
- '채택'은 **제안**이다(원칙 57). 확인 대장의 한 줄로 올라가고, 사용자가 확인한 것만 구현한다(원칙 34). 숫자('이번 달 14번 · 기관 3곳')가 제안의 근거가 된다.
- '이미 됨'은 확인 대장을 거치지 않는다(문구만). 다만 그 문구는 안내문이라 **역할별 점검 루프**에서 한 번 눌러 본다.
- 차수마다 평가 단계(PROCESS 5단계)의 입력에 이 목록을 넣는다 — "지난 차수에 가장 많이 막힌 셋".

## 만들 때 주의(완전체 기준)
- 모으는 표가 늘어나도 답이 늦어지면 안 된다 — 답을 보낸 **뒤에** 기록한다.
- 기관 간 분리(원칙 39): 기관 사용자는 자기 요청의 '이제 됩니다'만 받고, 목록은 LX 만 본다.
- 가짜 데이터 0: 목록이 비면 "아직 막힌 요청이 없습니다" 한 줄(공통 빈 상태).
