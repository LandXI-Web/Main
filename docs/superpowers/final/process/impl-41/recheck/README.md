## 5. 남은 것
1. **IPv6(::1) Docker 길 막힘**(2-②) — 근본은 Docker Desktop 의 IPv6 전달. 게이트웨이는 127.0.0.1 로 피했고, **워커 · 전국 작업기는 다음에 켤 때 같은 설정을 씁니다**(지금 하트비트 정상). 그 작업기를 맡은 쪽에 알려 주셔야 합니다. Docker 다시 켜기는 vLLM · DB 를 함께 멈추므로 하지 않았습니다.
2. **관리자 인프라 · 공유 데이터 탭 4~6초** — GPU 표(`ops.py` 전력 판정의 표본 스트림 다시 읽기)와 탭마다 20여 요청. `ops.py` 는 다른 작업이 고치는 중 — 끝난 뒤 표본 읽기를 줄이거나 관리자 첫 요청 묶기.
3. **지역 숫자에 같은 필지 · 같은 규칙이 두 번 들어가는 줄 8개**(남원 정본 R3 와 비닐하우스 카드 판 R3 가 같은 필지) — 설계대로(지역 = 모든 줄)이지만 '의심 건'이 8 많게 셉니다. 큰 숫자 '현장 확인 필요 n필지'는 필지를 한 번만 세서 영향 없음. 줄 하나로 셀지 결정 사항.
4. 서버 시험 중 이번 바퀴와 무관한 데이터 · 환경 드리프트 6건(`test_impl22_core` 새 클래스 '묘지' 남음 · `test_impl3_imagery` 표준 영상 마스크 · `test_impl4_fixes` 연결 겹침 · `test_impl5_project` 두 건(재학습 사유 · 개인 할당 100GB) · `test_live_infer` 모델 미리 올리기 — GPU 다른 작업 중). 고장 화면은 없음.
5. 전남광주 기관 배포본 이름 4줄이 '전남광주통합특별시 … · 적용'(V-World 원천 이름 · 원칙 268 전에 만든 줄) — 관리자 화면에 글로는 안 보이지만 서버 응답에는 있음. 데이터베이스 직접 수정은 하지 않았습니다(이름 바로잡기 도구로 같이 고칠 일).
6. Redis 순간 끊김(WinError 64) 때 500 이 몇 건 — 2-② 와 같은 원인으로 보임(127.0.0.1 로 바꾼 뒤 0).

## 이런 것도 필요하지 않을까요? (원칙 57)
1. **게이트웨이 감시가 DB · Redis 길도 함께 보기** — 누가 왜: LX 관리자. 이번처럼 Docker 길이 막히면 감시가 게이트웨이만 거듭 다시 켜다 실패합니다. 'DB 에 못 붙음'을 먼저 알리면 원인을 바로 압니다.
2. **관리자 첫 요청 묶기**(지난 바퀴 제안 그대로) — 공유 데이터 · 인프라 탭 4~6초 → 2초 안팎.
3. **해외 큰 숫자 서버 보관**(지난 제안 그대로).
