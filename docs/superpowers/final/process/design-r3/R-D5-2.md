# R-D5-2. 재학습은 누가 판단하나 — 역할 후보 · 기준과 가이드 · 추천안 (다시 기획)

> 지위: 사용자 확인 전 제안(확인 요청 2차 D5-2 "보류 → 다시 기획"). 코드는 고치지 않았다.
> 사용자 원문(09-30): "재학습을 누가 판단하느냐가 중요. 기준과 가이드도. 프로젝트장? LX 관리자?" · 원칙 46 "승인·반려·재학습 같은 판단은 누가 하는지와 그 기준·가이드를 먼저 정한다."
> 2차 설계의 '신호 5개 → 다음 할 일 1개(계산 한 곳)'는 **판단 재료**로 유지한다. 이 문서는 그 재료를 **누가 보고 결정하고, 누가 실행을 허락하는지**를 정한다.

## 1. 재학습이 왜 '판단'인가(비용과 책임)
- **GPU·전력**: 학습은 한 장을 몇 시간 잡는다. 두 장 동시 고부하 금지(09-26 셧다운) — 대기열이 지키지만 **언제 넣을지**는 사람 결정.
- **결과가 바뀐다**: 새 모델 = 새 버전(R-D2 §5) → 적용 지역의 결과가 달라진다. 기관이 이미 현장 확인 중인 목록에 영향.
- **표본이 있어야 한다**: 오탐 신고·맞음 표본이 모여야 재학습이 의미 있다. 신호가 울려도 표본이 없으면 '표본 확인'이 먼저.
- 그래서 판단은 둘로 나뉜다: **① 필요한가(모델·업무 판단) ② 지금 돌려도 되는가(자원·순서 판단).**

## 2. 역할 후보별 장단점
| 후보 | 장점 | 단점 | 어울리는 판단 |
|---|---|---|---|
| **프로젝트장**(모델을 만든 팀의 장, R-D3) | 데이터·라벨·정밀도·오탐 원인을 가장 잘 안다 · 빠르다 · 책임이 분명(자기 프로젝트) | 자원 전체를 못 본다(다른 프로젝트와 GPU 경쟁) · 프로젝트마다 엄격함이 다를 수 있다 | ① 필요한가 |
| **LX 직원(구성원 누구나)** | 신호를 본 사람이 바로 | 책임이 흩어진다 · 같은 프로젝트에서 요청이 겹친다 | 신호 확인·표본 정리까지 |
| **LX 관리자** | GPU·전력·대기열·기관 영향을 전체로 본다 · 기준을 한 벌로 지킨다 | 모델 세부를 모른다 · 병목 · 판단이 늦어진다 | ② 지금 돌려도 되는가 |
| **자동(신호가 기준을 넘기면 대기열에)** | 일관 · 빠름 | GPU 무단 실행(전력 규칙 위반 위험) · 표본 없이 돌 수 있음 · 책임 없음 | 없음(권장 표시까지만) |

## 3. 추천안 — 두 단 판단
```
신호 계산(자동, 한 곳)  →  프로젝트장 '재학습 요청'(필요한가 · 근거판 자동 첨부)
                        →  LX 관리자 승인(지금 돌려도 되는가 · 순서·시간대 · 반려 사유)
                        →  작업 대기열(GPU 한 장 규칙) → 학습 → 결과 확인 → 새 버전(R-D2) → 갱신 배포(결재)
```
| 단 | 누가 | 보는 것 | 결정 | 남는 것 |
|---|---|---|---|---|
| 신호 | 플랫폼 | 신호 5(§4-1) · 표본 수 · 마지막 학습 | '재학습 권장' 표시(강제 아님) | 서비스 관리 표 · 프로젝트 6단 다음 할 일 |
| ① 필요한가 | **프로젝트장** | 근거판(신호 값·기준·표본·오탐 원인 비율·적용 지역 수) | **재학습 요청** / 기준값 조정 제안 / 표본 더 모으기 / 안 함(이유 한 줄) | 요청 + 근거판 + 예상 GPU 시간 |
| ② 지금 돌려도 되는가 | **LX 관리자** | 요청 근거판 + 대기열·전력·다른 학습·기관 영향(현장 확인 중 목록) | **승인**(시간대·순서 지정) / **반려(사유 필수)** | 결재 이력 · 반려 사유는 프로젝트 이력에 |
| 실행 | 대기열 | 한 장 규칙 · 전력 상한 | 자동 | 학습 로그 |
| 뒤 | 프로젝트장 → 관리자 | 정밀도 비교(전 · 후) | 새 버전 공개 요청(R-D2) → 승인 · 갱신 배포 결재 | 버전 이력 |
- 프로젝트장이 없는 서비스(옛 데이터·담당자 퇴직)는 관리자가 프로젝트장을 먼저 지정한다(R-D3 §3-4). 빈 자리에 판단을 두지 않는다.
- 관리자 승인이 **자동 통과**되는 예외는 두지 않는다(GPU 는 항상 사람이 연다). 다만 관리자 결재함에 '권장(신호 2개 이상)' 표시로 우선순위를 돕는다.

## 4. 판단 기준과 가이드(초안 · 초기값은 관리자 설정에서 조정)
### 4-1. 신호 5(2차 설계 유지) → 권장 할 일
| 신호 | 기준 | 권장 |
|---|---|---|
| 표본 정밀도 | 표본 ≥ 20건이고 정밀도 < 80% | 재학습 후보 (표본 < 20 → '표본 확인' 먼저) |
| 실제와 다름(AI 잘못 봄) | 30일 · 서비스 × 기관 · ≥ 5건 | 재학습 후보 (다른 이유는 세지 않음) |
| 마지막 학습 경과 | > 365일 | 재학습 후보 |
| 새 영상 시점 | 적용 지역에 새 영상 등록 | 재분석(재학습 아님) |
| 신뢰도 흐름 | 최근 평균 신뢰도가 이전보다 0.05 이상 하락 | 재학습 후보 |
- 우선순위: 재학습 > 기준값 조정 제안 > 표본 확인 > 재분석 > 갱신 배포 > 없음. 첫 화면·서비스 관리·관리자 화면이 같은 계산.

### 4-2. 프로젝트장 가이드 — '재학습 요청' 전 확인 5가지(시트에 체크로 보임)
1. 오탐 원인 비율: '실제로는 대장대로(AI 잘못 봄)'가 오탐의 절반 이상인가? (기준 엄함·대장 오래됨이 많으면 재학습이 아니라 기준값 조정·대장 확인)
2. 새 표본: 마지막 학습 뒤 새로 확인된 표본(오탐·맞음) ≥ 20건인가? 적으면 '표본 더 모으기'.
3. 지역 쏠림: 오탐이 한 읍면·한 기관에 몰려 있나? 몰리면 그 지역 영상·라벨을 먼저 보강(실태조사 명세: "오류 비율이 높은 지역이 곧 다음 학습 데이터 수집 지역").
4. 영향: 적용 지역 n곳 · 현장 확인 진행 중 목록 n건 — 큰 변경(2.0)이 되면 기관에 미리 알림.
5. 자원: 예상 GPU 시간(표본 수로 자동 추정) · 대기열 상황 — 요청 메모에 희망 시간대.
- 다섯 중 1·2가 '아니오'면 시트가 '재학습' 대신 '기준값 조정 제안 / 표본 더 모으기'를 권한다(막지는 않음 · 이유를 적으면 요청 가능).

### 4-3. LX 관리자 가이드 — 승인 판단 4가지
1. 전력·대기열: 지금 학습 중인 작업이 있나(있으면 순서만 정하고 승인) · 야간 시간대 우선.
2. 요청 근거: 신호 2개 이상 또는 프로젝트장 이유가 있음.
3. 기관 영향: 현장 확인 진행 중인 기관이 있으면 '완료 뒤 갱신 배포는 별도 결재' 확인.
4. 사업 우선순위: 목표일이 가까운 프로젝트 먼저(R-D3 사업·기간).
- 반려 사유 고르기: GPU 여유 없음(시간대 재요청) / 표본 부족 / 근거 부족 / 기준값 조정으로 먼저 / 기타(한 줄). 반려는 요청을 없애지 않고 프로젝트 6단 '다음 할 일'로 되돌린다.

## 5. 화면(공통 패턴)
| 장면 | 어디 | 패턴 |
|---|---|---|
| 신호와 권장 | 서비스 관리 표(서비스 · 기관 · 버전 · 정밀도(표본 n) · 실제와 다름 30일 · 마지막 학습 · 권장) · 프로젝트 6단 다음 할 일 | 표 + 칩(권장은 잉크, 색 0) — P-3·P-4 |
| 근거판 | 행을 열면 우측 서랍: 신호 5줄(값·기준·넘김 표시) · 오탐 원인 비율 · 새 표본 수 · 적용 지역·현장 확인 중 · 예상 GPU 시간 | P-3 서랍 |
| 재학습 요청 시트 | 서랍 안 1차 버튼 '재학습 요청' → 가이드 5 체크 + 메모 + 희망 시간대 → 확인 대화 | P-9 확인 대화 · 토스트 "재학습을 요청했습니다" |
| 관리자 결재 | 결재함 종류 칩 '재학습 실행' → 승인/반려 시트(근거판 + 대기열 상황 + 시간대·순서 입력 + 반려 사유 필수) | P-2 승인/반려 |
| 진행 | 프로젝트 2단(학습) 회차 +1 · 대기열 위치 · 진행 막대 | P-6 불러오는 중(막대만) |
| 뒤 | 결과 확인 → 정밀도 전·후 → '새 버전 만들기'(R-D2) | — |

## 6. 구현 계획(확인 뒤)
1. 서버: 신호 계산 한 곳(2차 설계) · 재학습 요청(근거판 스냅샷·가이드 체크·메모·예상 시간) · 결재 종류 '재학습 실행'(승인 시 시간대·순서 → 대기열 예약, 반려 사유) · 프로젝트 회차 · 이력.
2. 화면: 서비스 관리 표·서랍·요청 시트 · 결재함 항목 · 프로젝트 다음 할 일 · 관리자 설정(기준값).
3. 실증: 신호 2개가 울린 서비스 1개 → 프로젝트장 요청 → 관리자 **반려(사유)** → 재요청 → 승인(야간) → 대기열 예약 확인(실제 학습 실행은 사용자 승인 뒤 · GPU 한 장) → 정밀도 비교 화면.

## 7. 완료 기준
- 관리자 승인 없이 학습이 대기열에 들어가는 경로 0(직접 버튼 포함).
- 요청 시트에 가이드 5 체크와 근거판이 자동으로 채워짐 · 반려 사유가 프로젝트 이력과 서비스 서랍에 보임.
- '재학습 권장' 수가 첫 화면·서비스 관리·관리자 화면에서 같은 값.

## 8. 확인받을 것
1. **R-D5-2** — 판단 주체: ⓐ 두 단(프로젝트장이 필요 판단·요청, LX 관리자가 실행 승인 · 반려 사유) — 추천 / ⓑ 프로젝트장 단독(관리자는 사후 기록만) / ⓒ LX 관리자 단독(직원은 신호만 봄).
2. 기준·가이드 초안(§4)은 ⓐ~ⓒ 어느 쪽이든 같이 확인.
