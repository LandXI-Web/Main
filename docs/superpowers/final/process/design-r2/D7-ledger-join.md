## 6. 설계 결정(제안)
1. **결합은 서버 한 곳에서.** 지금은 브라우저가 먼저 결합하고 4열로 줄여 서버에 보내 사전·단계가 둘로 갈린다. 원본을 그대로 서버로 보내고(개인정보 열은 서버가 버림), 사전 §3·사다리 §4·실패 §5를 한 곳에 둔다. 브라우저는 열 미리보기·열 확인 표·진행·결과만.
2. 열 확인 표의 '뜻' 목록을 §3으로 넓힌다(지금 5개: 필지 번호·지번·상태·날짜·사용 안 함). 자동 인식이 맞으면 표는 접혀 있고 '확인' 한 번.
3. 지번 뒤 지목('1답'), 나뉜 주소 열(시군·읍면·리), '법정동' 열, 소재지에 시군 접두 — 표본에서 나온 변형 4가지를 첫 목표로.
4. 대장 형식 등록(LX 직원, 서비스 만들기)은 같은 사전을 쓰고, 기관이 올릴 때 그 서비스의 형식이 있으면 먼저 그 형식으로 맞춰 본다.

## 7. 구현 계획
1. **서버**: 사전 통합 · 사다리 ③④ 보강(소재지 여러 열 이어 붙이기·시군 접두) · 지번 뒤 지목 분리 · 전각·'외 n필지' 정규화 · 실패 유형 코드 → §5 문구 표 · 행 단위 재결합 API · 결과 세 숫자 API.
2. **기관 화면**: 원본 그대로 올리기 → 열 확인 표(넓힌 뜻) → 진행 → 세 숫자 + 못 맞춘 행 표 + 행 수정·재결합. '마쳤습니다'는 결과 도착 후.
3. **실증**: 표본 5개(운봉·병영(나뉜 열)·달동(법정동)·덕과(지목 붙음)·화양(시군 접두)) + 확인자가 만든 CSV(CP949) 1개 → 결합률·실패 유형이 표대로. 두 기관.

## 8. 완료 기준
- 표본 5개 모두 결합률 90% 이상(덕과면 포함), 못 맞춘 행은 §5 유형으로 분류되어 표에 보임.
- 못 맞춘 행 1건을 표에서 고쳐 다시 결합 → 맞음으로 바뀜.
- '결합을 마쳤습니다'가 세 숫자와 동시에만 뜸 · 새로 고침 뒤 유지 · 개인정보 열 저장 0.

## 9. 확인받을 선택지
1. **결합을 서버 한 곳으로**(원본 그대로 전송, 개인정보는 서버가 버림) — ⓐ 서버 한 곳 / ⓑ 지금처럼 브라우저 먼저.
2. 정리표(대장 종류 · 열 사전 · 매칭 사다리 · 실패 안내)와 첫 목표 변형 4가지 — 확인 / 보류 / 반려.
