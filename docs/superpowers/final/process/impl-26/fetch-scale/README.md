# 구현 26 · 영상 호출 동시 수 단계 상향 + 자동 조절 장치 (10-13 사용자 허락 "그래 단계적으로 올려~")

브리핑 확인: (1) **GPU 한 장만 · 두 장 동시 고부하 금지 · nvidia-smi 는 조회만**: 전국 작업은 GPU0 한 장에서만 돌았다(GPU1 은 vLLM 상주 전력만). 사용률 · 전력 상한(70% · 140W)을 바꾸지 않았고 시스템 전력 설정도 건드리지 않았다. ## 멈춘 단계와 이유
**8에서 멈췄다(관리자 설정 fetch_max = 8 · 실제 값은 장치가 4–8 사이에서 고른다).**
1. 서버가 정상일 때 4와 8의 영상 읽기 대기가 같다(1.1초). 16으로 올려도 빨라지지 않는다.
2. 서버가 느릴 때 8은 응답 시간만 2배 넘게 늘렸다. 8에서는 응답이 한 번 크게 튀었다(12:14 · 375ms). 지시의 멈춤 조건('응답 시간 안정')에 걸린다.
3. 오전에는 국토지리정보원 서버가 장애가 날 만큼 불안했다. 우리 호출과 장애가 관련 있다는 증거는 없다. 장애 전 8단계의 부하는 초당 2타일 남짓이었고, 서버는 08시부터 이미 느려지고 있었다(4 · 예전 방식에서도 읽기 대기 12초 → 117초). 그래도 공공 서버이므로 더 올리지 않는다.

## 장애 때 '결과 0으로 끝난 칸' 되돌림 (`reset-outage.json` · `ngii-404-notice.txt`)
- 11:29–11:35 에 국토지리정보원 타일 주소가 502 · 시간 초과를 낸 뒤, **404 와 html 안내 페이지**를 줬다. 안내 글은 "현재 일시적인 접속 지연이 발생하여 서비스 이용이 원활하지 않습니다"였다. 예전 규칙(GDAL 설명 파일의 ZeroBlockHttpCodes 404 · 이번 새 읽기도 처음에는 같은 규칙)은 이것을 '영상 없음'으로 읽었다. 그래서 칸이 결과 0으로 8–16초 만에 '끝'이 됐다.
- 되돌린 것: **11:29 뒤에 끝났거나 돌던 하천 26칸 · 13.6㎢**(전주 덕진구 · 완산구). 칸을 todo(시도 0)로 바꾸고, 낮은 줌 면 · 작업 연결 · 그 작업들의 결과 묶음 파일을 지웠다. 11:42 에 다시 켠 뒤 모두 다시 분석해 결과가 나왔다(예: 금암동 건물 271).
- 예전 방식에서도 같은 장애가 났다면 같은 일이 생겼을 수 있다. 되돌린 뒤에도 결과가 0인 '끝' 칸이 남아 있다. 농지 5칸(10-12 14:41–17:08 · 2.05㎢)과 하천 4칸(10-13 · 태평동 · 서신동 · 강흥동 · 도덕동 · 1.16㎢)이다. 하천 뒤 두 칸은 안내 페이지를 오류로 세게 고친 뒤에 끝났다. 모두 전주 도심 칸이라 정말 0일 가능성이 크지만, 확인은 하지 않았다(아래 남은 것).

## 남은 것
1. 결과 0으로 '끝'난 칸 9개(농지 5 · 하천 4 · 모두 전주 도심)가 정말 0인지는 확인하지 않았다. 다시 돌리려면 사용자 결정이 필요하다.

4. 워커 로그(`f1b-a6000-0.log`)는 재시작 때마다 지워져서, 영상 읽기 대기 원본은 `summ.py` 가 단계를 끝낼 때마다 읽어 표에 남겼다.

## 제안 — 이런 것도 필요하지 않을까요?
1. **관리자 한 줄에 '남은 약 n일'** — 누가·왜: LX 관리자. 오늘처럼 서버 상태로 일정이 두 달 ↔ 2주로 바뀐다. 진행 %만으로는 이것을 알 수 없다. 같은 장부의 남은 날을 함께 보이면 된다.
2. **'영상 서버 응답 없음' 한 줄** — 누가·왜: LX 관리자. 장애 때 작업기는 이제 기다리지만, 화면에는 '학습 장비가 놀 때 차례로'로만 보인다. 왜 멈췄는지(영상 서버 접속 지연) 한 줄로 보이면 문의가 줄어든다.
3. **국토지리정보원 이용 범위 · 호출 한도 정식 확인** — 누가·왜: LX(운영 책임). 오늘 장애의 원인을 알 수 없다. 공공 서버를 전국 단위로 쓰는 만큼, 권장 동시 수와 시간대를 공식으로 받아 두면 안전하다.
